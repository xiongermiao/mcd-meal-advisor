# mcd-meal-advisor 性能基线实测（方式 C）

> 实测时间：2026-10-25 13:06–13:09　门店：某门店
> 口径：真实调用只读接口，**未建单、未兑换、未调用任何写接口**。用户交互为模拟（我按最短合法回答推进），表中单列。
> 声明：墙钟耗时由本地时间戳测得，**含模型推理间隙**，比接口真实耗时要大；但三次测试同一把尺子，横向可比。调用次数是硬数据。

## 三、发现 1：单次点餐内部没有重复，重复全发生在追问

这是本次测试最反直觉的结论，**改错方向会白花功夫**：

测试 1 的 7 次调用里，**没有任何一次是重复取数**。8 个字段都不同、都有明确用途。

重复全部发生在**第二次提问**之后：

- 测试 2 三次调用 **100% 是重复**。用户只是问了个卡路里，模型重新拉了 160 行营养库、重新定位了门店、重新拆了一遍套餐。
- 测试 3 四次调用里 **3 次是重复**。

对应 skill 原文（第一章「适用前提」）：

> 一切实时数据以接口返回为准：门店、营业时段、菜单、价格、券、库存、积分余额都**不缓存、不假设、不复用上一轮的值**。

**这条规则的代价不是"每次点餐慢"，而是"每次追问都重新点一遍餐"。** 而追问恰恰是最高频的交互。

## 四、发现 2：三次只读调用本可并行，白等 37 秒

测试 1 的真实依赖图：

```
call1 门店（必须先做，后续都要 storeCode）
   ├── call2 account      ┐
   ├── call3 store-coupons ├─ 四者互不依赖，都只依赖 storeCode
   ├── call4 meals        │
   └── call5 nutrition    ┘
        └── call6 套餐详情（依赖 call4 的 productCode）
             └── call7 核价（依赖 call6）
```

| | 串行实测 | 并行后 |
|---|---|---|
| call2+3+4+5 | 9,621+8,780+8,873+13,044 = **40,318 ms** | 取最慢者 = **13,044 ms** |
| 测试 1 总计 | 85,417 ms | **约 47,900 ms** |

**单这一条就能省 37.5 秒，占测试 1 总时长的 44%。** 而 skill 第二章到第八章通篇没有提过并行，主流程表是纯线性八步，模型自然逐条排队。

## 五、发现 3：简单需求被八步吸收，实证如下

| 用户实际问的 | 需要的最少调用 | skill 实际走的 | 浪费 |
|---|---|---|---|
| 「这个套餐多少卡」 | 1 次（营养库命中单品名 + 上下文已有套餐构成） | 营养库 → 定位门店 → 拆套餐 = 3 次 | **+200%** |
| 「我有什么券」 | 1 次 `query-my-coupons` | 定位 → account → store-coupons = 4 次 | **+300%** |

两个具体成因，都在 skill 里写死了：

1. **营养问题被迫先定位门店**：`query-meal-detail` 必填 `storeCode`，而营养库里**没有套餐**（只有单品，160 行里查不到"培根蔬萃双层牛堡三件套"）。于是"查一个套餐的热量"必须：拉全量营养库 → 找门店 → 拆套餐 → 加总。一个纯数据问题被拖进履约流程。
2. **查券被绑到门店上**：第 2 步规定用 `query-store-coupons`，而它必填 `storeCode` → 必须先过第 1 步定位。但"我卡包里有什么券"用 `query-my-coupons`（无参）一次就能答全，且返回的有效期比 store-coupons 更完整。

## 六、发现 4：返回体量与规则的错配

| 调用 | 体量 | 问题 |
|---|---|---|
| `list-nutrition-foods` | ~8 KB / 160 行，**每次都全量** | 无入参、无过滤，只为查 3 个单品也得吃 160 行 |
| `query-meal-detail` | ~12 KB | 含全部特调组的 selectedKey/unselectedKey，实际只需 3 个 choices |
| `query-meals` | ~11 KB | 含 categories 重复聚合（同一 code 出现多次） |

单是 `query-meal-detail` × 2 + 营养库 × 2 = **约 40 KB**，占了全部工具返回的 62%，而真正参与决策的信息不到 3 KB。

## 七、对应三个改动点的收益预估

| 改动 | 作用点 | 调用数变化 | 耗时变化 |
|---|---|---|---|
| **查询分流** | 测试 2、3 | 7 → 2（两次追问合计） | −60 s |
| **按变更复用** | 测试 2、3 | 再省 1 次（营养库/门店/套餐详情命中上下文） | −20 s |
| **只读并行** | 测试 1 | 7 次不变 | **−37 s** |
| 三者叠加 | 三次测试 | **14 → 约 6 次** | **167 s → 约 65 s，降 61%** |

**保留下单前核验的代价**：`calculate-price` 与 `create-order` 之间的严格校验（六查、确认单、异常闭环）一次都不减，因为它们在测试 1 里只占最后 13.5 秒，且这 13.5 秒买的是"不多建一单"。**砍前面 71 秒，留最后 13 秒。**

---

## 八、结论

1. **"禁止跨轮复用"是本次实测最大的单点浪费**，但它伤的是追问场景，不是首次点餐。改法不是删掉这条规则，而是改成「**变更即失效**」：只有发生变更的项（换门店、换时间、换商品、券被用掉）才作废，其余沿用并标注取数时刻。
2. **并行是零风险的最大收益**：`query-my-account` / `query-store-coupons` / `query-meals` / `list-nutrition-foods` 四者在拿到 storeCode 后完全无依赖，skill 里没有任何一句允许它们排队。
3. **查询分流要先解决一个数据结构问题**：营养库无套餐、`query-meal-detail` 强依赖 storeCode，这两条不解决，"查营养"永远要付 3 次调用的门票。可行解是在 skill 里维护一张「套餐 → 组成单品」的静态映射（套餐结构不随门店变），把门店依赖从这个路径上摘掉。
4. **下单前核验一分不砍**，且它在总时长里占比很小（13.5 / 85.4 = 16%）。

## 九、附：本次实测的完整接口签名要点（供改 skill 时引用）

- `query-my-coupons` 无参可调，返回 `title` / `couponCode` / `tradeDateTime`，**足以单独回答"我有什么券、什么时候过期"**，不需要门店。
- `list-nutrition-foods` 无参，返回固定 160 行 TSV 风格字符串，**无套餐**，只有单品名，含 `energyKcal / protein / sodium` 等 9 列。
- `query-meal-detail` 必填 `storeCode` + `orderType` + `beType` + `code`，返回 `rounds[].choices[]` 含 `isDefault` / `diffPrice` / `modification`。
- `calculate-price` 返回单位是**分**，实测 3950 = ¥39.50；`takeWayList` 返回 `eat-in` / `take-in-store`；**不返回原价与优惠明细**（`discount: 0`），"原价 50.5"这类信息接口不给。
- `query-nearby-stores` 的 `distance` 在 `searchType=2` 下有效（70 米），`longitude/latitude` 恒为 0，说明基准是搜索中心点而非实时定位。
