# mcd-meal-advisor 优化提案：下单 / 兑换的异常闭环

> 版本：20261025　状态：待评审，未落地
> 评审范围：仅「写操作（有副作用）」的异常路径，不涉及选品、营养、展示、履约定位等既有章节。

---

## 0. 结论速览

| # | 结论 | 影响 |
|---|---|---|
| 1 | **当前 MCP 没有幂等键参数**，`create-order` / `mall-create-order` 都是 `additionalProperties: false` 的封闭 schema，无 `requestId` / `clientOrderNo` / `idempotencyKey` | 原计划"复用同一键"落不了地，必须换成「查证式幂等」 |
| 2 | 现在只有「成功 / 失败」二态，缺**第三态：结果未知**。超时被当成失败是重复建单的直接来源 | 主流程第 6/8 步要加分支 |
| 3 | **兑换的风险远高于下单**：餐品单不支付会在 `expirePayTime`（约 15 分钟）后自动释放，积分扣了不会退 | 兑换的异常闭环优先级应高于下单 |
| 4 | `create-order` 返回体没有文档化的输出字段说明，**必须以 `orderId` 是否存在作为唯一成功判据** | 判据要写死，不能靠"没报错就算成" |
| 5 | `mall-create-order` 有 `status` 三态（1 全成 / 2 部分成功 / 0 全败），**部分成功当前完全没覆盖** | 需单列处理规则 |
| 6 | 需要新增 `references/failure.md`（约 90~120 行），主 SKILL.md 只插入引用与硬规则（约 +70 行） | 避免 SKILL.md 从 544 行继续膨胀 |

## 1. 先纠一个前提：幂等键在这个 MCP 上不存在

逐字段核对了两个写接口的 schema：

| 接口 | 现有参数 | 有无幂等键 |
|---|---|---|
| `create-order` | storeCode / orderType / beType / beCode / addressId / takeWayCode / reservationDate / items / withOrder / remark / needTableware / gmServiceCode | **无** |
| `mall-create-order` | skuId / spuCategory / addressId / count | **无** |

两者都是 `additionalProperties: false`，塞多余字段会被拒。

**由此得出的三条硬约束**：

1. **不能自己造幂等键**。往 `remark` 里写 `traceId=xxx` 是错的——`remark` 是用户可见的配送备注（限 50 字，会印在骑手单上），不是幂等字段，塞进去既不生效还会污染订单备注。
2. **不能假设"重发同一请求 = 同一订单"**。没有幂等键时，第二次调用就是第二个订单，MCP 层不会去重。
3. 所以幂等只能**在 skill 这一层做**，手段是三件套：**三态判定 + 写前快照 + 指纹锁**（第 6 节）。

> 如果将来 MCP 暴露了幂等键，规范见第 7 节，可直接替换。

## 2. 地基：先把接口分成"能重试"和"不能重试"

异常处理混乱的根源是没区分这两类。建议在第八章开头立一张表：

| 类别 | 接口 | 超时/失败能否直接重试 |
|---|---|---|
| 只读 | `query-nearby-stores`、`query-meals`、`query-meal-detail`、`query-store-coupons`、`query-my-coupons`、`list-nutrition-foods`、`query-promotions`、`delivery-query-*`、`mall-points-products`、`mall-product-detail`、`query-my-account`、`order-list`、`query-order`、`mall-order-list`、`mall-order-detail`、`campaign-calendar`、`now-time-info` | **可以**，超时重试无副作用；但重试结果必须覆盖旧值，不得两轮混用 |
| 计算 | `calculate-price` | **可以**，无副作用；但重试是为了拿最新价，不是为了"再算一次更便宜" |
| **写** | `create-order`、`mall-create-order`、`party-order-create`、`cancel-order`、`auto-bind-coupons`、`draw-lottery`、`mall-create-order` | **不可以**。默认禁止自动重试，必须先查证（第 4、5 节） |

一句话规则写进第七章：**只读可重试，写操作一律"先查后动"，查不出结果就不动。**

## 3. 核心模型：结果四态

把"成功 / 失败"扩成四态，每态一个动作。判据必须写到可以照着执行：

| 态 | 名称 | 判据（全部满足才算） | 唯一合法动作 |
|---|---|---|---|
| **S1** | 确认成功 | 返回体含 **`orderId`**（餐品单）／ `status=1` 且 `orderItemStatus=1` 且拿得到 `couponCodes`（兑换单） | 记账、交支付入口、写指纹 |
| **S2** | 确认失败 | 返回体完整、含明确业务失败信号（错误码 / 明确文案：库存不足、门店已打烊、时段不可下单、券已失效、积分不足、参数非法） | 分类后决定：参数类**改参重出确认单**；瞬时类（系统繁忙）**最多一次**重试，且重试前必须先做一次 S3 查证 |
| **S3** | 结果未知 | ① 调用超时 / 连接中断 ② 返回空、非 JSON、解析失败 ③ **无 `orderId`**（含只有状态码没单号）④ `mall` 单 `status=2`（部分成功） | **只查证，不重发**（第 4、5 节） |
| **S4** | 冲突 | 查证时发现已有单，但门店 / items / 金额与本次意图不一致（可能是用户自己在 APP 下的单，或上一轮遗留） | 停手，报给用户核对，**不覆盖、不取消、不追加** |

三条判据细化：

- **`orderId` 是唯一成功凭证**。出现"提示下单成功但没返回 orderId"，一律 S3，不得凭文案宣称成功。这条直接对应现有禁止事项「禁止把兑换成功当成下单成功」。
- **`status=2` 不是成功**。部分成功 = 成功的那部分要认，失败的那部分不许自动补——补一次就是第二次扣分。归 S3，走第 5 节的矩阵。
- **S2 也要看返回完整性**。返回体残缺（只有一句"失败"没有码）不构成 S2，按 S3 处理。宁可多查一次，不可少查一次。

## 4. 下单（`create-order`）异常闭环

### 4.1 三段式：写前快照 → 调用 → 分流查证

```
第 7 步确认单已出 + 用户明确下单指令
        ↓
【写前快照】调用一次 order-list（只读，安全）
           记下：baselineOrderIds（最近 5 单的 orderId + createTime）
        ↓
【调用】create-order，本地记录发起时刻
        ↓
   ┌────┴────┬─────────────┐
  S1        S2            S3
  ↓         ↓             ↓
下游      见 4.3       【查证，见 4.2】
```

写前快照只在第 8 步做一次，成本极低（无参调用），但它是后面判断"有没有多出一单"的唯一基线。**没有基线的查证等于没有查证。**

### 4.2 S3 的查证协议（照顺序做，不可跳步）

| 步 | 动作 | 判定 |
|---|---|---|
| 1 | `order-list` 取最近订单 | 与 `baselineOrderIds` 做差集 |
| 2a | 差集里**有**新单号 | → 取该 `orderId` 调 `query-order`，核对 storeCode / 门店、items 商品与数量、应付金额是否与本次一致 |
| 2b | 核得上 | 转 **S1**，补记成功。文案要说"刚才没返回，其实已经建好了"（见第 9 节） |
| 2c | 核不上 | 转 **S4**，停手，让用户去 APP 核对 |
| 3a | 差集**为空**（无新单） | 仍**不自动重发**。列为"疑似未创建"，进第 4 步 |
| 3b | 调用本身失败（order-list 也超时） | 转 **S3-不可查证**，直接告知用户去 APP 查，本会话不再尝试建单 |

> **关键认知：「查不到」≠「没建」。** `order-list` 可能不含未支付单，也可能有写入延迟。所以差集为空只能得"疑似未创建"，不能得"确认未创建"。

### 4.3 允许再次调用 `create-order` 的三个前提（缺一不可）

| 前提 | 说明 |
|---|---|
| ① 状态是 S2，或 S3 且查证差集为空 | 二选一 |
| ② 重发前**重新 `calculate-price`** | 中间可能过了几分钟：券被用掉、时段过期、价格变动。不重算就重发 = 拿旧价下单 |
| ③ **用户二次确认** | 必须说清"上一次没提交成功，我重新提交一次"，并给出重算后的新价。不得静默重发 |

三条任何一条不满足，就停在异常态等用户。这是"未确认失败不重发"的严格执行版。

### 4.4 真出现两单怎么办（兜底）

若发现两次调用都返回了不同 `orderId`（客户端自动重试导致），则以**最后一次**为准，另一单处理：

- 未支付 → `cancel-order`，`cancelReasonCode=2`（重复下单）。这个码官方就为这场景留的。
- 已支付 → **不代取消**，告知用户自己去 APP 或客服处理，并说明保留哪一单。
- 报告时两单号都要给出，不隐瞒多出来那一单。

### 4.5 券在下单环节失败的特殊分支

`create-order` 报券相关错误（券已用 / 券不适用本店）时：属 S2，但**不能仅重试**——必须先 `query-store-coupons` 重查可用券 → 剔除失效券 → `calculate-price` 重算 → **重出确认单**（金额已变）→ 再等用户确认。理由：券变了就是方案变了，按现有「级联失效」规则要重走第 4 步。

## 5. 兑换（`mall-create-order`）异常闭环

### 5.1 为什么兑换更危险

| 维度 | 餐品单 `create-order` | 兑换单 `mall-create-order` |
|---|---|---|
| 直接资产损失 | 不支付即无损失 | **立即扣积分** |
| 自动回收 | 有，`expirePayTime` 约 15 分钟未支付自动释放 | **无** |
| 重复后果 | 两单未支付，取消一单即可 | **积分被扣两次，退款要走客服** |
| 部分成功 | 不存在 | **存在（`status=2`）** |

结论：兑换的异常闭环必须比下单更保守，**默认动作从"查证"升级为"查证 + 冻结重试"**。

### 5.2 写前快照

兑换前必须记下三样（都是只读）：

1. `query-my-account` → 当前积分余额
2. `query-my-coupons` → 券清单（券名 + 张数）
3. `mall-order-list(size=3)` → 最近兑换单 orderId

### 5.3 四象限判定矩阵（S3 查证后）

> 前提：积分余额变化**不能单独当证据**——签到、别的兑换、过期结算都会让余额变。必须与 `mall-order-list` 交叉验证。

| 余额 | 有无新兑换单 | 券是否到账 | 判定 | 动作 |
|---|---|---|---|---|
| 下降 | 有，且 skuId 对得上 | 到账 | **S1 成功** | 正常继续：回第 4 步重算价 |
| 下降 | 有，`orderItemStatus=0` 或 `status=2` | 未到 / 部分到 | **S3-半完成（最危险）** | **禁止重兑**。明说"积分已扣、券未到"，给 `mall-order-detail` 的订单号，引导 APP 或客服；本会话不再尝试兑换该 sku |
| 下降 | **无** | 未到 | **S3-账务延迟** | 禁止重兑（余额已动说明极可能已执行）。告知"可能稍后到账"，让用户过几分钟再查，不自动补 |
| 未变 | 有 | — | **可疑** | 用 `mall-order-detail` 核对 `skuId` 是否为本次；不是本次就当历史单忽略；确认是本次但未扣分，报异常，不动 |
| 未变 | 无 | — | **等于未执行** | 可重试，但仍需用户二次确认，且重试前重查 `mall-product-detail` 确认还有库存与所需积分 |

### 5.4 `status=2` 部分成功的处理规则

根因是 `count>1` 时多件兑换可能部分失败。治理方式分两层：

- **事前规避（主）**：写死规则——**兑换 `count` 一律为 1，用户要多个就拆成多个串行订单**，每个单独验证成功后再发下一个。这样 `status=2` 在实践中几乎不会出现。（现有禁止事项已有"多商品兑换必须串行"，本条把它收紧为"单次 count=1"。）
- **事后处理（备）**：一旦仍出现 `status=2`，逐 `orderItem` 报告"哪个成功、哪个失败"，失败的项**不自动补兑**，等用户决定；成功项的券按已到账处理，参与后续核价。

### 5.5 兑换成功但券未回流时的连锁

兑换返回 S1 但 `query-store-coupons`（该门店）查不到这张券时：**不得进入第 4 步重算价**，因为拿不到 `couponId/couponCode`，`calculate-price` 算不出真实价。正确处理：

- 标"待核实"，告诉用户"兑换单已生成（单号 X），券可能还在到账中"
- 给一个明确等待口径："过 1~2 分钟我帮你重查"，或让用户自己在卡包确认
- 期间方案里的券项保留为「券兑换（待核实）」，不得当成已持有券去算价

## 6. 重复请求：三层防线

重复不只是"网络重试"，有三个来源，要分别防：

| 来源 | 表现 | 防线 |
|---|---|---|
| ① 接口层自动重试 | 同一次调用返回两个 `orderId` | **禁止自动重试写接口**（第 2 节）；真出现了走 4.4 兜底 |
| ② 用户重复指令 | 同一意图说两遍、跨回合反复要"下单" | **指纹锁**（下表） |
| ③ 上下文重建 | 会话恢复 / 新开会话后又点了一次 | **冷启动查证**：进入第 8 步前先 `order-list` 看最近 5 分钟有无同门店同类单；有就先问 |

### 6.1 方案指纹

```
指纹 = hash( storeCode | orderType | beType | beCode | takeWayCode
             | reservationDate | sorted(items: productCode×quantity×couponId)
             | 应付总额（分） )
```

用途：

- 指纹相同 + 已存在 S1 订单 → **拒绝建单**，回复"这一单已经下过了（订单号 X），不重复创建"，并给 `cancel-order`（理由 2）选项
- 指纹相同但金额不同 → 视为**不同方案**，允许下单，但必须重出确认单（价格变了就要重新确认）
- 指纹里刻意不含 `remark`、`needTableware`——这些不影响"是不是同一单生意"，含进去会让去重失效

### 6.2 单飞锁

同一指纹在**任一时刻只允许一个在途写调用**。含义：

- S3 状态下，指纹锁保持占用，新的"下单"指令一律先转查证，不允许开第二个请求
- S3 的结果没定论之前，**不得开始新一轮核价覆盖上下文**（否则查证时无法比对金额，也容易顺手重下）

## 7. 幂等键规范（前瞻，MCP 支持后可直接启用）

如果将来接口暴露 `requestId` / `clientOrderNo` / `idempotencyKey` 之类字段，规则写死四条：

1. **一键一逻辑单**：键在"用户确认下单"那一刻生成一次，此后该逻辑单的所有重试都复用它。
2. **键不得因重试而变**：重试时重新生成键 = 幂等失效，比不传键更糟。
3. **键与指纹绑定**：指纹变（换商品 / 换店 / 换时间 / 换券），必须生成新键，否则会撞上旧单。
4. **键落账**：键要在会话内可查（"本会话已用键 X 下过单"），否则上下文重建后又生成新键。

---

## 8. 超时口径

不要在 skill 里写死平台不存在的秒数，写策略：

- 以工具调用的返回或客户端超时为准；**没有返回明确业务错误，就不构成 S2**
- 等待期间不得对用户宣称"正在下单"以外的任何结论（禁"应该成功了""可能失败了"）
- 超过可接受的等待后（建议 60 秒，标为**建议值、非平台事实**）转 S3 话术，并开始查证
- **"慢"不是失败**，不得因为慢而立即重发——这是重复建单最常见的真实诱因

## 9. 异常态的展示与话术

### 9.1 版式冲突的解法（必须先定，否则执行时会乱）

现有铁律是"一条消息只有 1 个 `##`，且 `##` 只留给金额"。异常态下金额可能还没确定，需要补充规则：

| 态 | `##` 放什么 | 金额去哪 |
|---|---|---|
| S1 成功 | `## 已下单 · 订单号 XXX` | 正文写应付总价（上一轮确认单已核过） |
| S2 失败 | `## 没有下成 · 原因一句话` | 不出金额；给改后的重算价时用正文加粗 |
| S3 未知 | `## 提交结果未知 · 正在核对` | 不出现金额，也不用旧价兜底 |
| S3 查证后已建 | `## 其实已经下单成功 · 订单号 XXX` | 正文写应付总价（以 `query-order` 返回为准） |
| 兑换半完成 | `## 积分已扣，券未到账 · 请勿重复兑换` | 正文写"扣 N 分，余额 A→B" |

原则：**异常态的消息里，`##` 让给"结论"，因为此刻用户最需要知道的是"我的钱/积分怎么了"，不是"多少钱"。**

### 9.2 固定话术（可直接抄进 skill）

**S3 刚发生时**
> 提交后没有收到确认返回，**我不会重复提交**，先查一下这一单到底建没建。

**查证后已建（4.2-2b）**
> 查到了：这一单其实已经建好，订单号 `XXX`，应付 ¥Y（与刚才核价一致）。刚才只是返回慢了一步，**不用再下一单**。请扫码或用麦当劳 APP 完成支付。

**查证后无新单（4.2-3a）**
> 系统里没看到新订单，**大概率是没提交成功**。要我重新提交一次吗？重新提交会按当前价格重算（上次核价是 HH:MM）。

**兑换半完成（5.3 第二行）**
> 积分**已经扣了**（余额 A → B），但券还没到账，兑换单号 `XXX`。这种情况**请不要重复兑换**，否则会二次扣分。你在 APP 里能看到这张单，需要的话可以找客服催一下券。

**重复指令（6.1）**
> 这一单刚才已经下过了，订单号 `XXX`，不用再下一单。如果确实要再来一份，告诉我，我按加量重新核价。要是刚才那单不想要了，我可以帮你取消（未支付的才取消得掉）。

## 10. 禁止事项增量（建议直接追加到第七章）

- 禁止在写接口超时、无返回、未拿到 `orderId` 时**重发**同一请求。
- 禁止把「超时 / 慢 / 没看到返回」当成失败。
- 禁止在没有 `orderId` 的情况下宣称"已下单""已兑换"。
- 禁止用 `remark` 或任何业务字段承载自造的幂等/追踪标识。
- 禁止查证时把 `order-list` / `mall-order-list` 的"查不到"直接说成"没下单"然后重发。
