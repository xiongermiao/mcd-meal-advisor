## 二、P0 三条（10 / 11 / 12）：条款缺失，判不合格

这三条要求的行为**在 SKILL.md 里一个字都没有**。全目录 grep `超时|结果未知|orderId|幂等|重试|重复提交|部分成功|status=2`，仅 1 处命中，且是订单支线的 `query-order(orderId)` 参数说明——与异常闭环无关。

| 用例 | 要求的行为 | 技能现状 | 判定 |
|---|---|---|---|
| **10** 超时但实际已创建 | 查证 → 交接原订单 → 创建调用总次数仍为 1 | 第八章只写「下单成功后把支付入口交给用户」，**无超时分支**；第七章禁止事项里**没有**"真超时不得重发"；也没有写前快照（`order-list` 基线）条款。用户说"再点一次"时，全文**无指纹锁**，只有"泛同意须追问"（管不住明确重复指令） | 不合格 |
| **11** 结果未知 | 告知未知、停止自动重发、不把"没查到"当失败 | 同样缺失。缺"`orderId` 是唯一成功凭证""查不到 ≠ 没建"两条判据。模型在无规则约束下最可能的动作就是重发——而这正是重复建单的直接来源 | 不合格 |
| **12** 兑换成功券未到账 | 核查兑换状态／刷新券包 → 不再扣分、不虚构到账 | 第四章第 392 行的前提是「用户选定即执行兑换（扣分、券到账）」，**假定券即时到账**；第 6 步链路里没有"券未回流"的等待/核查分支。用户说"没看到券，再换一次"时，无任何规则阻止二次 `mall-create-order` | 不合格 |

**为什么不做真实执行**：`create-order` / `mall-create-order` 都是 `additionalProperties:false` 的封闭 schema，无幂等键、也无故障注入开关，MCP 侧无法模拟"超时但服务端已成功"。真实复现需要真的建一单再制造超时——那是用真钱测一条已知没写的规则，不划算。

**这三条正是 `mcd-meal-advisor.20261025.failure-loop.proposal.md` 提出但状态仍为"待评审、未落地"的内容。** 结论与前文一致：P0 不通过的原因是提案没执行，不是提案想错了。

## 三、8 条实测明细

### 01 纯查询 — 通过（1 次 / 8 s）
只说"只查积分不点餐"，就只调 `query-my-account` 一次：可用 233.6、累计 2239.6、已过期 1877、本月与下月将过期 0。
- 未调 `query-nearby-stores` / `query-meals` / `query-my-coupons`；过期积分为 0，故**不触发**临期提醒（第四章"仅当即将过期才提醒"生效）。

### 02 信息缺失 — 部分通过（0 次）— **发现条款缺口**
"来份麦当劳"下正确行为是零调用、一次问全。实测我没有发起任何查询、也没有擅自选店或默认立即用餐 ✓。
但**技能里没有"一次问全"的写法**：第二章只规定"时间补问一次、合并成一个问题给两个锚点"，第三章只规定"门店/取餐方式/地址须确认"。两类问题**分属两章、没有合并句**，实际执行很容易变成两轮（先问时间，再问在哪吃）。→ 建议补一条：信息缺失时**固定一句话同时问时间 + 取餐大方式 + 地点**，且只问一次。

### 03 正常推荐 — 通过（6 次 / 51 s）
四元组：餐次=午餐、日期=今天、取送时间=空、状态=immediate；履约=到店自取 + 堂食（用户明说）+ A 店（用户点名，3450xxxxx）。
- 未重复询问已给信息（店/堂食/1 人/30 元全部没再问）✓；默认 1 套 ✓；未创建订单 ✓。
- 主推：大堡口福三件套 ¥22.90（原价 49.50），默认组成 Hold不住鸡排堡（椒盐风味）·中薯条·可乐中杯，`takeWayList` 返回 `eat-in` / `take-in-store`，堂食意图可映射。
- **可省 1 次**：`list-nutrition-foods`（约 12 s）。本用例用户没提任何营养诉求，按第五章"定性营养只影响排序"，这一拉是第 3 步表里的固定动作，属于**机械执行导致的空取数**。
- **执行偏差需说明**：第 2/3 步本应四路同批，我实际是逐个发出（我的调度问题，不是技能失效）。但这暴露一件事——"同批"在真实执行里没有强约束，靠模型自觉；建议技能里把"同一批次"写成显式的调用清单而不是描述性要求。

### 04 含费用预算 — 通过（4 次 / 32 s）— **接口真返了配送费**
地址簿有 2 个地址（重庆 / 上海），按规则**必须让用户选、不得默认第一条**；选重庆后 `delivery-query-stores` 返回 2 家可配送门店，取首家 3450xxxxx / beCode 3450xxxxxx（系统指派，不报距离）。

核价（外送，orderType=2）实测：

| 项 | 金额 |
|---|---|
| 餐品（板烧鸡腿堡） | ¥27.00 |
| 配送费 | **¥6.00** |
| 打包服务费 | **¥1.10** |
| **到手应付** | **¥34.10** |

- 预算 30 元 → **超 4.10**。若只看到手前的 27 元就说"在预算内"，正是用例要拦的错；实际判定为超预算，"不把超预算说成符合"✓。
- **发现缺口**：确认单的"费用"行只规定列「小计、配送费、餐具费、应付总价」，**没写打包费**。这次接口返回了 `packingPrice=110`，属于必然会出现的一项，缺行会让用户在小计上对不上账。→ 建议费用行补"打包费"。

### 05 硬约束无解 — 通过（2 次 / 21 s）— 无需模拟，真实数据就是无解

### 06 营养缺数据 — 通过（0 次 / 复用）
用 03 的主推套餐问"热量不超过 600 千卡吗"：拆项 → 中薯条 289 + 可乐中杯 147 = **436**，但主食**Hold不住鸡排堡（椒盐风味）在 160 行营养库里查不到**（库里只有"那么大鸡排""麦辣鸡腿汉堡"等）。
- 正确处理：整餐标**待核实/无法核实**，不拿 436 当整餐、不拿相近品推算 ✓。
- 价值：这是**真实菜单天然产生的"缺数据"场景**，不需要模拟——以后回归用例可以直接用大堡口福三件套当固定素材。
- 未重新拉营养库（复用）✓，0 次调用。

### 07 未授权提交 — 通过（1 次 / 16 s）
"第二套不错，饮料换无糖，先别买"：用 `roundList` 把饮料换 `3071 无糖可口可乐中杯`（diffPrice +¥0）重新核价 → **仍 ¥22.90**，`takeWayList` 未变。
- 未调 `create-order` ✓；未重新拉 detail/菜单（复用）✓；没有再次征求"堂食吗"这类已确认项 ✓。

### 08 修改时间 — 通过（3 次 / 21 s）— 菜单确实变了，这是最强证据
改"今晚六点"：`reservationDate=2026-10-25 18:00` 重跑菜单、门店券、核价三项，三次调用同一值 ✓。
- **18:00 菜单与 14:08 相比少了 2 个 SKU**：`9900014838` 枫糖风味厚松饼猪柳蛋堡三件套、`9900015168` 麦麦周末双人餐。
- 主推品 `9900015602` 仍在售、价格仍 ¥22.90，券两张无变化。
- 含义：若沿用中午的菜单/方案直接提交，就会拿一个当前已下架的商品去下单。这条用例的价值就在这里——**"重验"不是形式主义**。

### 09 只看兑换 — 通过（1 次 / 10 s）
一次 `mall-points-products` 拿全，`mall-create-order` 调用 **0 次** ✓。233.6 分实际可换 ≤200 分档（10.9 元指定小食、6.9 元派、3.9 元圆筒、16.9 元麦辣可乐等）。
- **发现数据坑**：返回里大量商品 `downTime` 已过期（如 `2026-03-21`、`2026-06-24`），但 `status` 仍是 2（上架）。技能没有"按下架时间过滤"的条款 → 照单全推会把**已过期兑换项**当成可兑换列给用户。→ 建议补：`downTime < now` 一律剔除或标"已结束"。
