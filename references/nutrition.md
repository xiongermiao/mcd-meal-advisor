# 营养数据取数与对齐

仅在用户提出营养 / 健康诉求时加载。主文件「约束 3」的关注指标台账引用本文件。

## 一、接口事实（实测，勿凭记忆改写）

`list-nutrition-foods`：

- **无任何入参**，一次返回全量扁平表（实测 160 行）。**整会话只取一次**：营养值是配方属性，不随门店、时间、活动变化，重复取数没有任何信息增益。会话内再次需要营养数据时直接用已取的那份，不必重取。
- 字段：`productName / nutritionDescription / energyKj / energyKcal / protein / fat / carbohydrate / sodium / calcium`。
- **只有 productName，没有 productCode** → 与门店菜单只能按名称对齐，禁止用商品编码互推。
- **全是单品，没有套餐** → 套餐必须拆到底才能取营养。
- **有规格变体**：中 / 大 / 小 / 迷你薯条、可乐中 / 大 / 小杯，各自独立成行。
- **有重名**：实测「小杯玉米杯」「纯牛奶（盒装）」各出现两次。
- `nutritionDescription` 基本为 null，偶有「能量约鲈鱼1条」「能量约猕猴桃2个」这类描述串 —— **不可机读，不得引用**。

## 二、单位与精度

| 字段 | 单位 | 用法 |
|---|---|---|
| energyKcal | 千卡 | **以它为准**，不用 energyKj 换算（接口两者已并列给出） |
| energyKj | 千焦 | 仅备查，不展示 |
| protein / fat / carbohydrate | 克 | 取整到 1g |
| sodium / calcium | 毫克 | 取整到 1mg |

热量按 10 千卡取整，并冠以「约」。

## 三、对齐六条（按顺序执行）

1. **只按 `productName` 全名匹配**。营养库无 code，不得跨来源拼接。
2. **规格必须对齐**：中薯 ≠ 大薯 ≠ 小薯 ≠ 迷你薯，可乐中杯 ≠ 大杯。规格串用是本场景最常见的错。
3. **三级匹配，逐级降级，任一环节不唯一即拒绝**：

   | 级 | 动作 | 判据 |
   |---|---|---|
   | L1 归一化 | 去空格、统一全半角、去括号；括号内是规格词时保留该规格词 | 归一化后**完全相等** |
   | L2 包含 | 营养库名须**完整出现**在菜单名中，且两者长度差 ≤ 4 字 | 满足则进 L3 |
   | L3 双向唯一 | 该营养库名在全库**只出现 1 次**，且菜单侧**只有 1 个**商品能被它完整包含 | 双向都唯一才接受 |

   - 三级都不过 → 标「无数据」，**禁止回退到模糊匹配或相似度计算**。
   - 例：「牛气满满」⊂「牛气满满套餐」，营养库唯一、菜单侧唯一 → 通过；「麦香鱼」可被「麦香鱼」「麦香鱼套餐」同时包含 → 一对多，**拒绝**。
   - 白名单内的纯书写差异（括号、全半角、连字符、「堡 / 汉堡」）在 L1 消化，不进入 L2。
   - **规格词位置重排**仍允许：菜单写「薯条（中）」而营养库写「中薯条」时，按「规格词 + 主词」重排后再比对一次；仍不匹配即标「无数据」。
   - 通过 L2/L3 的命中**不直接采信**，须按第 6 条标注并验证。
4. **禁止近似替代**：找不到同名项 → 该品标「无数据」，不得用相近品推算、不得取同类均值、不得按「差不多」心算填。
5. **重名处理**：取首次出现的行；两行数值不一致 → 标「数据冲突，待核实」，不自行择一。
6. **营养库里有「整套餐行」，用错量级会差一倍以上**。实测有一批行的名字本身就是整套餐（「牛气满满」495、「"苹板"支撑Pro」476、「专"薯鱼"你」463、「绝代双翅」469、「果然多肉」478、「蜜汁快乐」258），与同名单品的口径完全不同。**必须走加总反证才能升级为可信**：

   ```
   L2/L3 命中后 → 先标「按营养库同名项匹配，未校验」，可用但不作准
     ↓ 本次会话恰好拆了这个套餐（第 4 步拿到 rounds）
   拆出单品 → 加总 → 与该行比对
     ├─ 热量差 ≤2% 且 蛋白、钠两项也吻合 → 升级「已验证」，写入缓存，后续直连
     └─ 否则 → 判定同名不同物，拒绝，记一条「陷阱映射」（菜单名 + 被拒营养库名 + 实测差值）
   ```

   - **判据必须三项同时吻合**，不能只看热量：495 这类数字容易撞车，单项吻合是巧合，三项同时吻合基本只可能是同一物。
   - **不得用字符串规则代替验证**：「牛气满满套餐」剥掉「套餐」= 495 ✓；「麦香鱼中套餐」剥掉「套餐」→ 325 ✗（实测 761，错 436 千卡 = 134%）。同一个剥离动作一对一错，区别不在字符串，而在营养库那条记录到底是单品还是整套餐——**从数据本身看不出来，只能靠加总反证**。
   - 映射以 **`code` 为主键**，名字只作索引：实测 `query-meals` 与 `query-meal-detail` 对同一编码 9900005460 给出的名字不同（「麦香鱼套餐」/「麦香鱼中套餐」），名字本身不稳定。
   - 陷阱映射一旦记录，后续直接跳过 L2/L3，不再试探。

## 四、整餐算法

套餐 → `query-meal-detail` 的 `rounds` 取默认搭配（`isDefault=1` 的 choices）→ 逐项按上述六条匹配 → `值 × 数量` 加总 = 整餐值。

> **`query-meals` 不返回套餐构成**：餐品对象只有 7 个字段（name / image / currentPrice / originalPrice / discountType / canWithOrder / withOrder），没有 roundList。拆套餐只能走 `query-meal-detail`，而它必填 `storeCode`——所以「查一个套餐多少卡」在无门店上下文时，要么先定位，要么按主文件「营养支线」的降级处理，**不得为了查营养反问用户在哪家店**。

- **捷径**：若该套餐已在第 6 条校验中升级为「已验证」整套餐行，直接取该行数值并标「官方套餐数据」，不必拆解。这是唯一允许跳过拆解的情形。
- 拆不出明细（接口只给套餐名、无 rounds）→ **整餐值只能标「待核实」**，不得拿部分明细合计冒充整餐。
- 用户换配（换小食 / 饮料）后必须重新加总，不得沿用旧值。
- 数量取用户实际购买份数，不是菜单里的套餐份数。

## 五、对照样例（实测值，供校验口径）

| 商品 | kcal | 蛋白 g | 脂肪 g | 碳水 g | 钠 mg |
|---|---|---|---|---|---|
| 中薯条 | 289 | 4 | 12 | 38 | 165 |
| 大薯条 | 379 | 6 | 16 | 50 | 216 |
| 可乐中杯 | 147 | 0 | 0 | 36 | 0 |
| 无糖可口可乐中杯 | 0 | 0 | 0 | 1 | 35 |
| 板烧鸡腿堡 | 391 | 23 | 17 | 35 | 1041 |
| 麦辣鸡腿汉堡 | 485 | 24 | 24 | 42 | 1208 |
| 麦乐鸡5块 | 213 | 12 | 12 | 13 | 422 |

两个校验点：

1. 中薯条 1210kJ / 289kcal ≈ 4.186，说明 kJ 与 kcal 自洽，可直接采信 kcal。
2. 无糖可乐 0 千卡但钠 35mg；可乐中杯 147 千卡但钠 0 —— **热量与钠不能互推**，这是主文件禁止跨指标推断的实测依据。

## 六、拿不到数据时怎么写

统一写「无数据，待核实」，并说明缺的是哪一项。不得写「大概」「估计在」「应该没问题」。

## 七、整套餐行实测记录（2026-10-25，用于校验口径）

一正一反两个案例，改口径或怀疑数据时用它们复测。

**正例 · 牛气满满套餐（9900009245）**：默认搭配 = 培根蔬萃双层牛堡 + 小杯玉米杯 + 无糖可乐中杯

| | kJ | kcal | 蛋白 | 脂肪 | 碳水 | 钠 | 钙 |
|---|---|---|---|---|---|---|---|
| 加总 | 2073 | **495** | 26 | 24 | 42 | 764 | 79 |
| 营养库「牛气满满」 | 2073 | 495 | 26 | 24 | 42 | 764 | 79 |
| 差 | 0 | **0** | 0 | 0 | 0 | 0 | 0 |

七项指标零误差 → 营养库的整套餐行是官方按组合精确算得，不是估算，可直连。

**反例 · 麦香鱼中套餐（9900005460）**：默认搭配 = 麦香鱼 + 中薯条 + 可乐中杯 = 325 + 289 + 147 = **761 kcal**

剥掉「套餐」命中营养库「麦香鱼」325 → **错 436 千卡（134%）**。这条必须永远走拆解，或走陷阱映射跳过。

**附带参照**：同为培根蔬萃双层牛堡，牛气满满套餐（玉米杯 + 无糖可乐）495 kcal，培根蔬萃双层牛堡三件套（中薯 + 可乐中杯）878 kcal——**名字几乎一样，差 383 大卡**。营养结论永远不能由"套餐名相近"推出。
