# 配送型履约（麦乐送 / 团餐）

**何时读**：用户提到外送、麦乐送、送到家、团餐，或本次要用 `delivery-query-addresses` / `delivery-query-stores` 时。

**到店自取与得来速不读本文件**——那两条走主文件第三章的到店型规则。

## 一、外送门店择优（多家可配送时）

**实测事实**：`delivery-query-stores` 对同一地址会返回**多家**可配送门店，但返回字段里**没有 distance、没有配送费、没有预计送达时长，也没有门店地址**。可用字段只有 `storeCode` / `beCode` / `storeName` / `reservation` / `reservationTimeOptions` / `businessStatus` / `businessStartTime` / `businessEndTime`。

所以"挑最优"不能靠直觉上的最近／最便宜／最快——**这些数据根本不存在**。按四步走，顺序不可调：

1. **硬筛营业**：`businessStatus=false` 的剔除；
2. **硬筛时段**：`scheduled` 用 `reservationTimeOptions` 判断目标时刻能否**预约**；`immediate` 用 `businessStatus` + `businessStartTime/EndTime` 判断**当前是否在营业时段内**（`reservationTimeOptions` 通常只列尚可预约的段，当前正在进行的那段可能不在其中，不能拿它判断"现在能不能送"）。不满足的剔除；
3. **取返回顺序首家**：剩下多家时用接口返回的第一家（接口本身已按可服务性排序），**不自行编排序理由**。禁止写"这家最近""这家最快""这家配送费低"，没有数据支撑；
4. **缺货才换店**：只有在 query-meals 阶段发现目标品类在该店无在售／售罄，才依次试下一家。换过店必须在确认单标注"该地址可配送 N 家门店，本单由 X 店承接"。

三种边界：

- **只剩 1 家**：直接定，不提问。
- **0 家**：直说"该地址不在配送范围"，给"换地址"和"改到店自取"两个出口，**不得静默改成到店自取**。
- **用户点名某家店**：在返回列表里按 `storeName` 匹配；匹配不到就说"该地址可配送的门店中没有 X 店"，**不得拿别家顶替**。

## 二、配送型展示义务（少一条算没推荐）

1. **报地址不报店址**：报的是**配送地址**；门店只给店名，**不报门店地址、不报距离**（接口也不返回）；
2. **标指派对**：写"系统按配送地址匹配"，不能只甩店名让用户以为是自己选的；
3. **不编时效、不编费用、不编远近**：字段里没有预计送达时间、配送费、距离，就不要写"约 30 分钟送达""这家配送费低""这家最近"。

## 三、配送型回归断言（必过）

| 输入 | 正确行为 | 错误行为 |
|---|---|---|
| **"叫个外卖，送到我家"** | 查地址簿 → 回写完整地址等确认 → 确认后才查可配送门店 | 先问"你要哪家店"；或跳过地址直接查菜单 |
| **"麦乐送，20 分钟内送到"** | 地址确认 → 查可配送门店 → 取首家 → 查菜单；**不承诺送达时效** | 编"约 20 分钟"；或让用户在两店之间选 |
| **该地址可配送 2 家门店** | 硬筛营业与时段 → 取首家 → 确认单标"本单由 X 店承接" | 让用户选店；或写"这家最近" |
| **该地址 0 家可配送** | 说"不在配送范围"，给换地址／到店自取两个出口 | 静默改成到店自取 |
| **用户指定某家店外送** | 在可配送列表按店名匹配，命中则用，未命中直说没有 | 拿另一家顶替却不说明 |
| **已确认地址后用户改了地址** | 等同换门店：重查可配送门店 → 菜单、券、价格、配送费全部重做 | 只改地址，菜单与价格沿用 |

## 四、团餐的特殊性

**团餐在参数链路上与麦乐送一致**（`orderType=2` + `beCode` 来自 `delivery-query-stores`），所以按配送型处理。但团餐若涉及**门店自提或现场服务**，门店会重新变成用户的决策项——该分支尚未实测，遇到时按到店型走门店确认，并把"团餐门店是否需用户指定"标为待核实，**不要凭本条硬套**。

团餐另需 `gmServiceCode`（来自 `query-meal-assistance`），`calculate-price` 与 `create-order` 都要传。
